## 슬라이드 5. R1Pro 입력·출력 규격 정합성

### 화면 문구

| 항목 | 구현 규격 |
| --- | --- |
| 카메라 | Head → left wrist → right wrist |
| 상태 | 61차원 proprioception |
| 행동 | 23차원 whole-body controller 입력 |
| RGB-D tensor | `[B, 3, 4, 224, 224]` |
| Action chunk | `[B, 12, 23]` |
| 초기 실행 길이 | `execute_steps=1` |

### 발표 설명

상태 61차원에는 base velocity, 양팔·gripper·trunk position/velocity와 end-effector 상태가 포함된다. 행동 23차원은 base 3, trunk 4, 양팔 14, 양쪽 gripper 2로 구성된다. 12-step 예측과 실제 한 번에 실행하는 길이는 별개이며 처음에는 한 step씩 실행한다.

### 화면 구성

행동 23차원은 “3 + 4 + 7 + 1 + 7 + 1”의 구간 막대로 표현할 수 있다. Gripper 관측 각 2차원과 행동 각 1차원은 다른 규격이라는 점을 발표자 설명에 남긴다.

## 슬라이드 6. 데이터 처리와 메모리 매핑

### 화면 문구

**Task/episode 선택 → revision 기록 → 영상 시간 정렬 → cache 생성**

- 공식 `tasks.parquet`와 JSONL fallback 지원
- Episode index·timestamp·RGB/depth offset 검사
- NPY mmap으로 RGB 전체 RAM 적재를 줄임
- 완료 metadata가 없는 cache는 로딩 거절

### 발표 설명

선택한 episode가 포함된 영상 shard를 내려받으므로 다운로드 크기가 episode 개수에 정확히 비례하지는 않는다. Mmap은 RAM 적재 문제를 줄이지만 cache 저장공간과 I/O 비용은 남는다. 학습 데이터 revision은 HF commit SHA로 기록한다.

### 화면 구성

`rgb.npy / depth.npy / states.npy / actions.npy / metadata.json`을 episode 폴더 안에 표시한다. 저장공간 수치는 부록 2에 배치한다.

## 슬라이드 7. Depth 단위 오류 방지

### 화면 문구

**Raw log12 코드와 공식 loader의 mm 출력을 구분**

1. Native 12비트 gray/Y plane을 직접 읽음
2. Log12 코드를 m로 복원
3. 0.01~10 m clip 및 nearest resize
4. 모델의 네 번째 채널로 depth/10 입력

### 발표 설명

공식 원본은 12비트 로그 영상이다. 메타데이터의 mm 표기는 공식 loader의 출력 단위이므로 raw pixel을 바로 mm로 해석하면 안 된다. 새 경로는 원본 코드를 직접 m로 복원하고, RGBA의 alpha를 depth로 사용하지 않는다.

### 화면 구성

“12-bit code → metres → depth/10” 세 단계 도식 옆에 “RGB와 depth를 별도 처리”를 표시한다.

슬라이드 하단 출처: [공식 info.json](https://huggingface.co/datasets/behavior-1k/2026-challenge-demos/blob/main/meta/info.json)

## 슬라이드 8. Depth가 실제로 학습되도록 수정

### 화면 문구

**문제:** Depth 가중치를 0으로 추가한 뒤 전부 freeze하면 depth를 계속 무시

**해결:**

- 기존 RGB kernel은 frozen 유지
- 새 depth kernel만 trainable
- 초기 RGB 응답 보존
- Gradient·가중치 업데이트·checkpoint 재로딩 검증

### 발표 설명

4채널 입력을 만들었다는 사실만으로 depth가 활용되는 것은 아니다. 새 depth kernel이 실제로 업데이트되는지 확인해야 한다. CPU 소형 모델에서는 nonzero gradient, depth 가중치 변경, 기존 RGB 가중치 보존을 확인했다. 이를 위한 backbone 연산 graph로 메모리 비용이 증가할 수 있으며 실제 A100에서 측정해야 한다.

### 화면 구성

RGB kernel에 “Frozen”, depth kernel에 “Trainable”을 표시하고 두 경로가 동일한 DINOv3 patch 입력으로 합쳐지는 그림을 사용한다. 성능 향상 수치를 추가하지 않는다.

## 슬라이드 9. A100 학습 실행 구성

### 화면 문구

- Python 3.11 + CUDA 12.6용 PyTorch 2.7.1
- 단일 A100, vision BF16 autocast
- Gradient accumulation·validation·checkpoint 재개
- 첫 실행: batch 1, accumulation 1, step 1
- 본 학습 전 VRAM·속도·loss 확인

### 발표 설명

서버용 의존성과 실행 스크립트를 작성했지만 실제 A100 환경에 설치한 것은 아니다. 예시 batch는 최적화 결과가 아니다. DDP가 없는 경로이므로 여러 A100을 사용하는 분산 학습이 구현된 것으로 설명하지 않는다.

### 화면 구성

“설치 검사 → 1-step → 작은 학습 → 확장” 순서를 표시한다. 전체 dependency 목록은 본문 대신 부록이나 상세 보고서를 활용한다.

## 슬라이드 13. A100 서버 확보 후 실행 순서

### 화면 문구

1. OS·A100·driver·저장공간 확인
2. 전용 환경 설치 및 CUDA/BF16 검사
3. 모델 weights + 소수 공식 episode 준비
4. RGB-D preflight → cache 생성
5. 실제 A100 1-step → checkpoint 로딩
6. 작은 학습 → RTX 평가 → 데이터·batch 확대

### 발표 설명

첫 성공 기준은 대회 task 성공이 아니라 실제 데이터가 디코딩되고, finite loss로 한 step을 수행하며, 저장한 checkpoint를 다시 로딩하는 것이다. 그다음 simulator에서 controller 순서·단위·reset을 확인한다. 큰 작업을 시작하기 전에 작은 실제 데이터 실험으로 연결 문제를 찾아야 한다.

### 화면 구성

여섯 단계 체크포인트 도식으로 표시한다. 서버 확보 전 가능한 다운로드·cache·CPU 검증은 별도 작은 메모로 표시한다.

오늘 성과는 실제 대회 학습을 시작할 기반과 CPU 근거를 확보한 것이다. 서버를 받으면 공식 episode와 A100 환경으로 동일 절차를 확인하고, RTX 시뮬레이터에서 정책의 실제 제어를 검증할 예정이다.

## 부록 1. 질문 대응 문구

### “코드만 A100에 복사하면 바로 학습할 수 있나요?”

학습 경로는 구현되어 있지만 Python/driver/의존성, DINOv3/BERT 가중치, 공식 시연 데이터와 cache를 준비해야 한다. 실제 서버 환경의 설치와 1-step 실행은 아직 검증하지 않았다.

### “A100 없이 할 수 있는 준비는 무엇인가요?”

코드 정리, 모델·데이터 다운로드, CPU 영상 디코딩과 cache 생성, CPU 계약 테스트가 가능하다. 서버용 preflight와 setup 스크립트는 CUDA/BF16 검사 때문에 CPU-only 환경에서 통과 대상이 아니다.

### “RGB-D를 지원한다는 것이 실제 depth를 학습한다는 뜻인가요?”

이번 구현은 depth 입력과 함께 trainable depth kernel을 추가했고 CPU 소형 모델에서 gradient와 업데이트를 확인했다. 실제 대회 성능 향상은 A100 학습 및 evaluation 이후 판단해야 한다.

### “24개 테스트는 실제 BEHAVIOR task 24개 성공인가요?”

아니다. 데이터 규약, 영상 처리, 통신과 소형 모델의 학습 가능성을 확인하는 CPU 테스트다. 실제 task 성공률은 측정하지 않았다.

### “A100에서 OmniGibson도 실행하나요?”

오늘 구성은 A100 학습·정책 서버와 지원되는 RTX 시뮬레이터를 분리한다. Isaac Sim의 공식 GPU 지원 조건과 환경 의존성을 고려한 구성이다.

### “여러 A100으로 분산 학습하나요?”

현재는 단일 GPU 경로다. DDP는 구현하지 않았으며 여러 프로세스 학습을 명시적으로 거절한다.

### “기존 TurboVLA release를 그대로 fine-tuning하나요?”

기본 경로는 사전학습 DINOv3/BERT를 사용하고 fusion/action을 새로 학습한다. 선택한 초기 checkpoint에서 core key와 shape가 맞는 tensor만 이식할 수 있으며 다른 benchmark의 action head가 변환 완료되었다고 간주하지 않는다.

## 부록 2. 발표용 수치·명령·출처

### 확인된 규격과 결과

| 수치 | 의미 |
| --- | --- |
| 61 | 상태 차원 |
| 23 | 행동 차원 |
| 3 | 카메라 수 |
| 4 | RGB-D 모델 입력 채널 수 |
| 224 × 224 | 기본 모델 입력 해상도 |
| 12 | 기본 예측 horizon |
| 1 | 초기 execute_steps 및 실제 서버 smoke-test 목표 step |
| 24 | 통과한 CPU 테스트 수 |
| 약 1.005 MiB/frame | RGB-D cache의 영상 array 계산값 |
| 약 1.77 GiB/minute | 30 Hz RGB-D 영상 array cache 계산값 |

Cache 수치는 상태·행동·파일 비용을 제외한 계산값이다. GPU 메모리 수치가 아니다.

### A100 환경에서 첫 학습 명령

모델·cache 경로 및 train/validation ID 설정 후:

```bash
export RUN_DIR=outputs/behavior-rgbd-smoke
RGBD=1 STEPS=1 BATCH_SIZE=1 GRAD_ACCUMULATION=1 \
  bash scripts/behavior_2026/train_a100.sh
```

### 검증 명령

의존성이 준비된 환경에서:

```bash
python -m unittest discover -s tests -p 'test_behavior*.py' -v
```
