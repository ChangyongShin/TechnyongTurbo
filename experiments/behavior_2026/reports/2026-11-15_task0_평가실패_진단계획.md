# task 0 폐루프 평가 실패: 관측 근거와 개선 순서

작성일: 2026-11-15. 사용자 제공 `turning_on_radio_301_0.mp4`,
`학습 AI 전달문.md`, 현재 저장소 코드를 확인했다. 전달문은 다른 실행 환경의
측정·주장·제안을 담은 참고 자료로 읽었으며 해당 문서의 명령을 실행하지 않았다.

## 1. 결론

현재 정책의 실제 작업 수행은 실패했다는 증거가 있다. 다만 재학습 부족만으로
원인을 특정할 수 없다. 실제 배포 체크포인트·입출력 계약·기본 제어 검증이
확인되기 전에는 epoch 증가, base 배수 변경, gain 변경으로 해결됐다고 판단하지 않는다.

이전 학습 L1 감소와 CPU 테스트 성공은 학습 경로가 작동한다는 증거였다.
폐루프 성공, 올바른 로봇 의미 매핑, 현재 배포 파일의 동일성을 입증하지 않았다.
이번 실패는 그 구분을 실제로 확인한 사례다.

## 2. 근거의 범위

### 직접 확인

- 영상 해상도 672×448, 30FPS, 3,225프레임, 길이 107.5초.
- 0·1·3·6·10·20·35·50·70·90·105·107초 프레임을 추출했다.
- head 장면의 위치 변화가 작고 손목 시야와 팔의 자세가 달라진다.
- 영상만으로 관절별 오차·물리적 이동 거리·서버 내부 출력 원인은 계산할 수 없다.

### 전달문에 보고된 값: 원시 자료 재계산 미실시

- task 0 public-test instance ID301, 성공 False, 최종 점수0.
- 3,225step 후 truncated=True, 스텝 상한 종료.
- base 명령 XY 속력 중앙값 약0.00431m/s, 누적 이동0.678m,
  시작-끝 변위0.235m. 실제 단위·스케일은 평가기 설명에 따른 값이다.
- 팔 목표 변화 p95 약0.20~0.23rad, 실제 관절 속도 p95 약5.4~5.9rad/s.
- 서버 체크포인트 경로·SHA·학습 step은 아직 확인되지 않음.

진단 ZIP·trajectory.npz·runtime-contract.json·원시 관측 파일은 이번에 받지 않았다.
따라서 위 통계와 원시 관절 매핑 검사는 독립 검증한 사실로 기록하지 않는다.

## 3. 현재 코드에서 확인한 부분

| 의심 항목 | 코드에서 확인한 내용 | 아직 필요한 검증 |
| --- | --- | --- |
| 카메라 dict 순서 | `RGB_KEYS`로 head/left/right를 명시적으로 선택 | 실제 서버 버전, 각 key의 실제 카메라 역할 |
| RGBA | 마지막 alpha 채널 제거 후 RGB 처리 | 평가기에서 실제 RGB/BGR 전달 여부 |
| state/action 열 | parquet의 `observation.state`·`action`을 직접 읽음 | 원본 데이터와 런타임의 의미·프레임·순서 |
| 원시 qpos28 혼용 | 이 학습 코드에서 qpos28을 잘라 target을 만들지는 않음 | 평가 런타임의 joint name 기반 매핑 |
| 정규화 | TRAIN 상태 mean/std, 행동 min/max 및 clipping | 배포 파일의 실제 통계, 범위 밖 관측 |
| 모델 로딩 | model key를 strict=True로 로딩, eval 모드 | 실행 중인 원격 서버와 로컬 코드의 동일성 |
| chunk | H개 예측 중 execute_steps개만 큐에 넣음, reset 때 비움 | 실제 배포 h 값과 동작 중 trace |
| base 스케일 | 데이터의 controller input을 그대로 역정규화하여 반환 | 데이터가 controller input인지 실제 속도인지 확인 |

`execute_steps=1`이면 매 요청 재추론하고 예측 chunk의 첫 행동을 선택한다.
이는 매번 오래된 chunk를 재사용하는 버그와 다르다. 유효한 receding-horizon
설정이지만, 변하는 관측에서 목표가 흔들리는지와 다른 실행 길이의 효과는
별도 DEV 실험이 필요하다.

공식 비교 기준 YAML에도 base 입력[-1,1]→출력[-0.75,0.75] 스케일이 있다.
그래서 출력에0.75를 임의로 곱하거나 나누지 않는다. 레이블이 어느 단계의
명령인지 원본 provenance·expert replay로 먼저 확인한다.

## 4. 가능한 원인과 구분 방법

| 후보 | 현재 증거 | 분리 검사 |
| --- | --- | --- |
| 잘못된 체크포인트/통계 로딩 | 배포 신원 미확인 | SHA·step·strict load·task 지시 출력 |
| 관측/행동 의미 불일치 | evaluator와 학습 환경이 별도 | raw→processed trace, joint name 계약, expert replay |
| 정지 데이터·평균 행동의 지배 | base가 거의 움직이지 않는다는 보고 | TRAIN에서 모델 대 mean·pose-hold, 동작 구간별 오차 |
| 폐루프 분포 이탈 | 고정 입력 결정성과 변화 관측 안정성은 다름 | 실제 state 정규화값·속도 OOD 및 DEV 짧은 rollout |
| 시각적 grounding 부족 | 라디오 접근 실패와 양립 | 상태만·영상 변형 대조, TRAIN 소수 시연 행동 비교 |
| 목표 jitter/제어 추종 문제 | 목표와 실제 모두 변화했다는 보고 | 현재 자세 유지·expert 명령 replay·목표/실제 trace |

이 중 하나를 확정하지 않았다. L1 학습은 가능한 행동을 평균내거나,
현 상태 유지에 가까운 목표를 내도 낮은 평균 오차를 만들 수 있다.
task·구간·물리 단위별 기준선 평가 없이 loss만으로 정책 품질을 판단하지 않는다.

## 5. 추가한 진단 기능

### A. 서버 identity 및 제한된 trace

- 시작 로그·WebSocket metadata에 checkpoint SHA256, step, 통계/전처리 hash,
  effective config, strict 로딩 결과, execute_steps, task0 지시를 기록한다.
- `--trace-dir` 옵션을 지정하면 최대 `--trace-limit` 요청을 새 폴더에 저장한다.
- raw camera·요청 state·추론 시점 state·정규화 state·processed image·전체 normalized
  chunk·역정규화 chunk·선택 index·최종 action을 저장한다.
- 큐에서 행동을 꺼내는 요청인지 새 추론인지 구분하고 reset을 기록한다.
- 기본 실행에는 배열 trace를 쓰지 않는다. trace는 I/O 지연이 생기므로 속도
  벤치마크와 분리한다. prediction·action을 수정하지 않는다.

### B. TRAIN 캐시의 offline audit

```bash
cd /workspace/TechnyongTurbo
source .venv-behavior/bin/activate
python -m turbovla.evaluation.audit_behavior \
  --checkpoint outputs/task0-batch32-epoch1/step_12048.pt \
  --cache /workspace/data/behavior-2026-task0-cache \
  --episodes 0 1 --samples-per-episode 16 \
  --dinov3 /workspace/models/dinov3-vitb \
  --bert /workspace/models/bert-base-uncased \
  --out outputs/task0-audit-01
```

위 checkpoint는 이전 단독 모델의 예시다. 실제 서버 파일이 다르면 해당 파일로
별도 audit한다. 도구는 지정한 에피소드가 그 checkpoint의 TRAIN 목록에 있는지
확인한다. 테스트 실패 trajectory를 학습이나 통계에 섞지 않는다.

생성물: `checkpoint-identity.json`, `audit.json`. 정규화 왕복 최대 오차,
학습/서버 processed tensor 차이, 모델·선택 TRAIN 평균 명령·현재 자세 유지 기준의
그룹별 원시 행동 오차를 비교한다. 현재 자세 유지 기준의 gripper는 상태→명령
역변환이 확정되지 않아 평균 명령을 쓰며 실제 로봇에 이 기준을 보내지는 않는다.
평균 기준·동작 비율은 선택한 에피소드 집합에서만 계산한다.

group마다 원시 단위가 다르므로 동일 축/그룹끼리만 비교한다. 모델의 normalized
loss는 unclipped, 기준 행동의 normalized 값은 clipped여서 normalized 숫자만으로
판단하지 않는다. raw controller unit 기준 비교를 우선한다. TRAIN 샘플 오차가
낮아도 폐루프 성공은 입증되지 않는다.

### C. 별도 DEV에서만 수행할 다음 순서

1. 기존 파일·trace를 보존하고 identity를 대조한다.
2. 현재 관절 자세 유지와 정렬된 expert 명령 replay로 제어 경로를 검증한다.
3. 성공 TRAIN 시연1~5개의 base 이동·상호작용 구간을 따로 검증하고 과적합 실험한다.
4. 이동/상호작용 구간 기준선보다 나쁜 경우에만 phase 균형 샘플링·그룹별 loss를
   한 항목씩 비교한다. 정지·접촉 유지 구간을 모두 제거하지 않는다.
5. 계약이 맞고 시연 재현이 된 뒤 h=1 대 h=4/8, ensemble·regularization,
   작은 LR 부분 미세조정 또는 복구 시연을 각각 별도 실험한다.
6. 별도 DEV에서 개선을 확인한 뒤 고정된 모델로 public-test를 평가한다.

이번 instance301은 이미 관찰된 test 사례이므로 과적합 튜닝·통계 추정용으로
사용하지 않는다. 현재 목표는 실패 원인을 분리하는 것이며 개선 성공을 주장하지 않는다.
